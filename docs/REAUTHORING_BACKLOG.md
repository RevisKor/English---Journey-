# Controlled Reauthoring Backlog

## Governing approach

This backlog applies the Curriculum Bible and the Reauthoring Operating System to the live audit. It deliberately **does not** schedule a universal lesson template or a blind rewrite. Each module begins with its architecture packet; each lesson is then authored from its own purpose, dominant archetype, density, selected stages, and meaningful evidence.

| Wave | Scope | Why this order | Required entry condition | Required exit condition |
|---|---|---|---|---|

| 1 | B2 Modules 3–10 | B2 is in progress, but 120 lessons lack adaptive experiences. | Module research ledger and 15-lesson architecture blueprint approved. | All seven operating-system gates pass for the module. |

| 3 | C2 level architecture, then Modules 1–12 | C2 has 180 fallback routes and needs the greatest complexity, independence, and mediation planning. | C2 level arc, module map, level frequency/density targets, and assessment map approved. | Every completed module has explicit experiences and a completion packet. |
| 4 | Targeted A1–B1 correction pass | Existing authored coverage is substantial; corrections must be audit-led, not destructive. | A module is flagged by repetition, density, disclosure, assessment, or visual-review evidence. | Only flagged lessons change; regressions and rationale are recorded. |

## B2 Module packet pattern

The same packet is repeated for B2 Modules 3–10, but the **content is never copied**. The architect selects a distinct module rhythm and activity-family distribution based on the particular module outcome.

| Packet element | Deliverable | Acceptance evidence |
|---|---|---|
| Research | CEFR/genre/context source ledger | Claims and examples are traceable. |
| Module architecture | 15 lesson blueprints | No arbitrary archetype rotation; retrieval links are natural. |
| Content | Bilingual activity corpus and experience map | Each activity contributes to the selected lesson purpose. |
| Pedagogy | Lesson-level PASS/FAIL review | Language load, Arabic supports, and transfer are level-appropriate. |
| Visual | First-view/disclosure review | The route answers “what, do, matters, next” without overload. |
| Assessment | Evidence and item review | Evidence matches the module outcome; distractors are plausible and accurately spelled. |
| Engineering | Tests, audits, type/build, preview | All controls pass and route rendering is reviewed. |

## Corrective priorities in existing content

| Priority | Evidence trigger | Scope of correction | Do not do |
|---:|---|---|---|
| A | Missing experiences or module blueprints | B2 Lessons 31–150; all C1/C2 lessons | Author activities before level/module architecture. |
| B | Repeated route signatures in one module | Highest-frequency A2 and B1 patterns | Rewrite a lesson merely because its archetype appears often. |
| C | Dense first view or support always visible | A1 beginner routes; any flagged light lesson | Hide required instructions or make Arabic help unreachable. |
| D | Weak transfer evidence or misleading quiz logic | Module reviews and assessments in every level | Add more questions without improving the evidence task. |
| E | Semantic meaning conveyed only by colour | Shared cards and workspace states | Replace useful semantic labels with decorative colour. |

## Guardrails

> A lesson may be short, quiet, and single-purpose. Completeness is measured by **learner value**, not by how many activity types appear on the screen.

No module can advance to a checkpoint when any of the following is true: it lacks a written architecture packet; its route signatures are repeated without rationale; an assessment evaluates content that the learner did not have a meaningful opportunity to use; the first view hides the next action; or the data passes but the learner route has not been reviewed.
